# JANUS Nexus Physical WAL Sidecar Gate

`JANUS_NEXUS_PHYSICAL_WAL_SIDECAR_GATE_V1` extends the certified storage evidence boundary to the physical SQLite `-wal` sidecar.

This gate exists because the v1.12 negative candidate demonstrated a critical storage fact: a surviving WAL can make a logically readable database view available even after explicit damage to the main database file. v1.12 hardened the main-file side first. v1.14 now gives a present WAL its own fail-closed physical envelope.

## WAL absent vs WAL present

A missing WAL is permitted as a normal checkpointed state:

```text
WAL ABSENT -> permitted if parent main-store gate passes
```

A present WAL is not treated as opaque helper state. It must pass a read-only physical inspection before the parent SQLite preflight is allowed to consume it.

## Physical envelope checks

For a present `-wal` file the reference checks:

```text
32-byte WAL header exists
magic = 0x377f0682 or 0x377f0683
format version = 3007000
page size is a valid SQLite page size
WAL page size == physical main-database page size
(size - 32) is an integer number of (24-byte frame header + page) frames
every parsed frame page number >= 1
```

The file is hashed before/after inspection to verify that the gate itself did not rewrite it.

## What is deliberately not checked yet

The current reference does **not** claim to validate the WAL checksum chain or salt continuity across frames:

```text
checksum_chain_verified = false
salt_chain_verified = false
```

Physical envelope PASS therefore does not mean full WAL semantic validity. It is only a prerequisite before the existing read-only SQLite `quick_check` and required-schema checks.

## Frozen corpus

`fixtures/nexus_wal_sidecar_holdout_v1.json` contains eight cases frozen before first execution:

```text
WAL-01 checkpointed healthy stores with no WAL sidecars
WAL-02 real SQLite WAL with valid physical envelope
WAL-03 corrupt WAL magic
WAL-04 WAL truncated below header
WAL-05 invalid WAL page size
WAL-06 incomplete WAL frame alignment
WAL-07 WAL/main page-size mismatch
WAL-08 damaged replay WAL blocks otherwise recoverable lifecycle state
```

Freeze SHA-256:

`e8b1b689525ae09ed95f631ae2aa89514d794acd4761bebb036ab98b3e07dfc3`

## Real WAL case

`WAL-02` does not use a synthetic header. The test opens the real lifecycle SQLite database, enables WAL mode, disables auto-checkpoint, commits an event while the connection remains alive, then inspects the resulting real `-wal` file.

This validates that the physical parser accepts at least the actual WAL representation generated by the CI SQLite runtime.

## Guarded recovery

`wal_guarded_recovery()` requires WAL physical checks first. Only when no present WAL fails does it delegate to the certified v1.12 storage preflight and then v1.10 manual recovery semantics.

A damaged replay WAL therefore blocks an otherwise recoverable stale lifecycle:

```text
LIFECYCLE HEALTHY
DISPATCH HEALTHY
REPLAY MAIN DB HEALTHY
REPLAY WAL DAMAGED
-> HOLD_WAL_EVIDENCE_UNAVAILABLE
-> NO LIFECYCLE MUTATION
```

The gate never deletes or repairs a WAL file.

## Claim ceiling

Passing this gate may establish only the frozen physical WAL envelope checks and fail-closed ordering before parent storage/recovery logic.

It does not establish:

```text
WAL checksum-chain validity
WAL salt-chain validity
semantic correctness of every frame
power-loss recovery
kernel-panic recovery
filesystem repair
WAL repair
cross-version SQLite compatibility outside tested assumptions
production database recovery readiness
automatic retry/restart/recovery
persistent daemon authority
external-effect authority
```

A natural next gate is checksum/salt-chain validation against both a real SQLite WAL and deliberately checksum-damaged frames, while retaining read-only/no-repair semantics.
