# JANUS Nexus WAL Checksum & Salt-Chain Gate

`JANUS_NEXUS_WAL_CHECKSUM_SALT_GATE_V1` extends the certified physical WAL envelope with the cumulative integrity rules defined by SQLite's WAL file format.

Primary format references used for this implementation:

- `https://sqlite.org/fileformat.html#checksum_algorithm`
- `https://sqlite.org/walformat.html`

The gate is read-only and strictly downstream of the certified v1.14 physical WAL parser.

## SQLite checksum semantics implemented

The 32-byte WAL header stores two checksum words at offsets 24 and 28. The header checksum is calculated over bytes `0..23` with initial state `(0, 0)`.

The checksum recurrence consumes data in 8-byte groups as two unsigned 32-bit words:

```text
s0 = (s0 + x0 + s1) mod 2^32
s1 = (s1 + x1 + s0) mod 2^32
```

Word byte order is selected by the WAL magic:

```text
0x377f0683 -> big-endian checksum input words
0x377f0682 -> little-endian checksum input words
```

Stored checksum words in the WAL header/frame header are always decoded as big-endian.

## Cumulative frame chain

For each physical frame, JANUS requires:

```text
frame salt-1 == WAL header salt-1
frame salt-2 == WAL header salt-2
```

Then the checksum state from the previous header/frame is continued over:

```text
first 8 bytes of frame header + complete database page body
```

The frame's salt fields and stored checksum fields are not included in that checksum input. The newly calculated pair must equal the two stored checksum words in the frame header.

The next frame begins from that calculated pair, creating one cumulative chain through the physically present WAL.

## JANUS strict physical-frame policy

SQLite recovery may scan until the first invalid checksum and treat later content as outside the valid WAL prefix. JANUS evidence admission deliberately uses a stricter rule for this gate:

```text
EVERY PHYSICALLY PRESENT FRAME MUST VERIFY
```

If any physically present frame has a salt or checksum mismatch, the evidence store is held rather than silently accepting a shorter valid prefix.

This can produce conservative false rejects. That is intentional for the current evidence-preservation role; it is not presented as SQLite's normal recovery policy.

## Real SQLite WAL case

The real-WAL case uses the CI SQLite runtime itself. Auto-checkpoint is disabled, several committed events are appended while a connection remains open, and the resulting live `-wal` bytes are inspected read-only.

The gate must establish:

```text
header_checksum_verified = true
salt_chain_verified = true
frame_checksum_chain_verified = true
verified_frame_count >= 2
bytes_unchanged = true
```

## Alternate byte-order vector

The CI host will normally exercise only the checksum byte order emitted by that SQLite build. To avoid leaving the second magic branch untested, the frozen corpus also includes an independent fixed vector for `0x377f0683` with a 4096-byte zero page.

Frozen expected checksum pairs:

```text
header = (656874011, 593918300)
frame  = (2599180039, 3840816585)
```

These constants are embedded as test data rather than generated by the implementation under test.

## Guarded recovery

`wal_integrity_guarded_recovery()` first requires checksum/salt integrity on lifecycle, dispatch and replay WALs. Only then may it delegate to v1.14 physical WAL, v1.12 storage and v1.10 manual recovery semantics.

A replay WAL with a valid physical size/header but invalid page checksum therefore blocks recovery without modifying the lifecycle row.

## No repair semantics

The gate never:

```text
truncates a WAL to a valid prefix
rewrites header/frame checksums
repairs salts
deletes a damaged WAL
resets replay state
resets dispatch intent state
grants retry or restart
```

## Claim ceiling

A PASS may establish checksum/salt integrity only for the frozen WAL cases and exact implementation.

It does not establish:

```text
cryptographic authenticity (SQLite WAL checksums are integrity checks, not MACs)
semantic correctness of page contents
correctness of transaction intent
power-loss recovery
kernel-panic recovery
filesystem repair
WAL repair
cross-version behavior beyond tested assumptions
exactly-once delivery
automatic recovery/restart/retry
persistent daemon authority
cross-host transport
external-effect authority
production database recovery readiness
```

The next useful gate after certification is to separate the valid-prefix concept from JANUS's strict all-physical-frames admission and test checkpoint/reuse tails explicitly, without weakening the certified strict evidence policy.
